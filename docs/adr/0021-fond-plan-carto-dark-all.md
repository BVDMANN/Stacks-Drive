# ADR 0021 — Fond Plan CARTO dark_all : la carte prend la palette « Nuit violette »

- **Statut :** acceptée (15/11/2026, demande du propriétaire ~07h44). **Note v2.53 ([ADR 0029](0029-carte-claire-quartiers-lisibles.md)) : REMPLACÉE — le fond sombre est retiré : noms de quartiers illisibles sur téléphone, retour au fond OpenStreetMap clair, sans clé.** **Note v2.50 ([ADR 0026](0026-carte-unique-pas-de-bascule-plan-satellite.md)) : le « fond Plan » est désormais LE fond — la bascule Plan/Satellite est retirée, il n'y a plus de second fond. Le correctif de l'accumulation de l'attribution à la bascule (décrit dans cette ADR) est devenu sans objet : l'attribution CARTO est posée une seule fois à la création de la couche.**
- **Contexte :** le 14/11 ~21h58, le propriétaire avait demandé de retirer le thème sombre de la carte (« Retire le thème sombre là-dessus ») parce que l'ancien fond sombre — tuiles Esri + filtre CSS sombre `.map-tiles-dark` (inversion + rotation de teinte) — lavait les détails et rendait la carte illisible ; le fond Plan était alors passé à OpenStreetMap clair (v2.41, ADR 0016). Le 15/11 ~07h44, il demande : « La carte à mes palettes de couleur demandées » — la CARTE ELLE-MÊME doit prendre sa palette « Nuit violette » (fond violet-nuit #191432, accents roses, palette v2.44). Cette nouvelle demande ne change pas l'exigence de lisibilité : elle exige un VRAI fond sombre détaillé, pas le filtre qui lavait tout. Le choix initial du lot (« CARTO light_nolabels ») est remplacé par cette décision.

## Décision

1. **Fond Plan = CARTO `dark_all`** (format documenté actuel, docs CARTO sept. 2026 : `https://basemaps.cartocdn.com/rastertiles/dark_all/{z}/{x}/{y}.png` — l'ancien format `{s}.basemaps.cartocdn.com/dark_all/…{r}.png` a été remplacé par celui-ci avant le push, car c'est le seul dont la documentation en vigueur garantit le fonctionnement avec clé), **pas `dark_nolabels`**. Les deux variantes sont le même fond sombre ; elles ne diffèrent que par les libellés imprimés :
   - `dark_all` imprime les noms de rues (autoroutes / grandes artères dès z13, primaires z14, secondaires / tertiaires z15, rues secondaires z16, voies de desserte z17 — style dark matter, `labels.mss`, section des noms de routes) et les noms de lieux en gris clair sur fond sombre.
   - `dark_nolabels` n'imprime AUCUN nom : ni quartiers, ni rues, ni lieux. Les libellés Drive ne nomment que les quartiers — les rues resteraient sans noms à tous les zooms.
   - Pour une appli de course, on s'oriente aux noms de rues : `dark_nolabels` est écarté sur ce critère (voir « Alternatives écartées »). `dark_all` est retenu, avec la table anti-double recalibrée (point 4).
2. **Clé API CARTO obligatoire** — fait nouveau et bloquant, découvert en lisant la documentation officielle (dépôt CartoDB/basemap-styles, README, consulté le 15/11/2026) : « Raster basemaps require an API key. Requests without a key are served with an "API key required" watermark. » Sans clé, CARTO sert une tuile filigranée « API KEY REQUIRED » à la place de la carte. La clé est gratuite (5 M de requêtes/mois hors commercial, 1 M en commercial ; au-delà, forfait « Basemaps Commercial ») et se crée sur https://carto.com/basemaps/apikey/ — c'est une clé de fond de carte, conçue pour être embarquée dans le code client (l'exemple Leaflet officiel la met dans l'URL). Elle se configure par `NEXT_PUBLIC_CARTO_API_KEY` (`.env.local` en dev, variables Vercel en production) ; sans clé configurée, l'URL part sans `?key=` et la carte affiche le filigrane. **C'est l'étape restante après le push, à faire par le propriétaire** (qui crée ses comptes lui-même) : créer la clé, la poser dans Vercel, redéployer. L'appli ne casse pas sans clé, mais le fond Plan est inutilisable tant qu'elle n'est pas posée. En v2.41, `dark_all` avait été écarté précisément parce qu'il exigeait déjà une clé (tuile « API KEY REQUIRED » vue par curl le 14/11) ; en v2.46 la clé devient une étape assumée du lot, pas un motif d'écart — le propriétaire a demandé la carte sombre, la clé en est le prix.
3. **AUCUN filtre CSS sur les tuiles.** Le fond est sombre nativement. La teinte violette #191432 n'est PAS dans les tuiles (CARTO dark_all est quasi noir, fond #090909 — voir point 5) : la palette « Nuit violette » est portée par les surcouches de l'appli, qui sont des éléments DOM sans risque — libellés Drive (texte clair + point rose), pictogrammes POI (fond #17112E, bordure rose), ligne d'itinéraire OSRM rose #FF4D8D, marqueurs chauffeurs, cercle périmètre 5 km, radar sarcelle (déjà en place depuis la v2.44) — plus le fond du conteneur `.leaflet-container`, passé en #191432 (`night-950`, `styles/globals.css`) : c'est la teinte violette visible pendant le chargement des tuiles et aux bords de la carte. Un VRAI fond violet (tuiles #191432) demanderait un style vectoriel personnalisé (MapLibre + tuiles vectorielles CARTO, couleurs modifiables à la volée) : c'est un lot ultérieur possible, non implémenté ici — voir « Alternatives écartées ».
4. **Table anti-double recalibrée, pas supprimée** (`lib/neighborhoods.ts`) : `NEIGHBORHOOD_OSM_LABEL_MIN_ZOOM` devient `NEIGHBORHOOD_CARTO_LABEL_MIN_ZOOM` (56 entrées), et une seconde table apparaît, `NEIGHBORHOOD_CARTO_LABEL_MAX_ZOOM` (borne haute par quartier, défaut 16). Le sort exact, quartier par quartier :
   - **PK5 RETIRÉ de la table** : `place=quarter` (Photon, 15/11), et AUCUNE règle du style CARTO — ni raster (`labels.mss`), ni vectoriel actuel (`dark-matter-gl-style`, couches `place_*`) — ne couvre `quarter`. CARTO n'imprime très probablement pas ce nom : le libellé Drive est le seul à l'écran et ne doit pas être masqué. Si la vérification live montre un double « PK5 », le remettre avec 14.
   - **Akanda, borne haute 14** : `place=city` (Photon, 15/11), et la règle `city` du style s'arrête à z14 (les libellés de ville disparaissent à z15). La règle `city` est en plus conditionnée par le rang (z8–14, rang ≤ 11/12/15 selon le zoom — rang d'Akanda inconnu) : si la vérification live montre « Akanda » absent à z12–14, retirer Akanda de la table des minimums.
   - **Les 54 autres entrées gardent leur zoom minimum v2.42 et la borne 16** : suburb / village / town s'arrêtent à z16 dans le style ; les minimums v2.42 sont conservés parce que CARTO utilise les mêmes données OSM (mêmes noms, mêmes objets `place`) et que ses premiers zooms par classe (suburb z12, neighbourhood z13) sont cohérents avec les z12–15 observés en v2.42 (l'écart vient des collisions entre libellés voisins).
   - **15 quartiers non reclassés** (Bikélé, Owendo, Alenakiri, Cap Esterias, Malibé, Essassa, Nkok, Nkoltang, La Peyrie, Camp de Gaulle, Igoumié, Akournam, Nkembo, Gros-Bouquet, Aéroport Léon-Mba — la recherche Photon n'a pas retrouvé leur objet `place`, ce qui ne prouve pas son absence) : le masquage v2.42 est conservé par prudence anti-double (40 des 42 quartiers classés sont `suburb`).
   - **Aucun quartier `place=neighbourhood`** parmi les 57 (Photon : 0) : la borne 17 (règle neighbourhood z13–17) ne s'applique à personne aujourd'hui ; si un quartier est un jour reclassé `neighbourhood`, ajouter `Nom: 17` dans la table des maximums.
   - Conséquence sur les comptes (vérifiés par `npm run docs:check`) : en Plan, 6 libellés Drive au zoom 12, 11 au zoom 13, **17 au zoom 14** (16 + PK5, qui n'est plus masqué), 14 aux zooms 15–16 (12 + PK5 + Akanda) ; en Satellite, 12 / 27 / 69 — inchangé.
   - **POI** (`lib/pois.ts`) : le champ `osmLabelMinZoom` devient `cartoLabelMinZoom`. Le style CARTO ne labellise que les parcs, stades (rang ≤ 3), cimetières (rang ≤ 3) et attractions (rang ≤ 3) — à partir de z15 (rang ≤ 1), z16 (rang ≤ 2), z17 (rang ≤ 3), z18. Les hôtels, écoles et ronds-points ne sont JAMAIS labellisés par CARTO : `cartoLabelMinZoom` est RETIRÉ de Park Inn by Radisson, du Rond-Point de la Démocratie, de l'Institut Français du Gabon et du Lycée National Léon Mba (leurs valeurs v2.43 venaient de tuiles OSM). Seul le Palais des Sports (stade, plus grande salle de la ville, rang ≤ 2 plausible) garde un champ (16) — approximation, à confirmer en live.
   - **Toutes ces plages sont des approximations dérivées du style, à confirmer en live après push** — voir « Preuves et limites ».
5. **Lisibilité : l'avertissement honnête du lot.** La lecture du style montre que dark matter est un fond « doux », conçu pour porter des données par-dessus, pas une carte routière lisible à elle seule :
   - fond #090909, libellés de lieux #444 (contraste ~2:1 sur #090909), libellés de rues #333 (~1,6:1), routes #030303 à #2a2a2a (filets), eau #262626, parcs #090909 (invisibles, même couleur que le fond), bâtiments #000 (contour #111).
   - Preuve indépendante : l'aperçu officiel du style (`.thumb.png`, dépôt basemap-styles, 512×512) ne contient que 51 couleurs, luminance moyenne 19,5/255, pixel le plus clair 59/255 — rien de lumineux nulle part.
   - Autrement dit : les noms de rues existent sur `dark_all`, mais ils sont imprimés en gris très discret, comme voulu par le style. C'est le même type de défaut que celui que le propriétaire a rejeté le 14/11 (détails lavés, carte illisible) — en natif cette fois, pas par filtre. La vérification live après push doit donc juger spécifiquement la lisibilité des noms de rues sur le téléphone du propriétaire, en plein jour : si c'est illisible, le plan de repli est le retour au fond OSM clair (v2.41, une bascule d'URL + de table) ou le lot vectoriel personnalisé (point 3). Ce lot ne prétend pas que la lisibilité est prouvée — il l'exige comme étape restante.
6. **Attribution : « © OpenStreetMap contributors © CARTO »**, texte exact exigé par la licence CARTO (exemple officiel Leaflet), visible sur la carte (contrôle d'attribution Leaflet, en haut à droite) et dans le pied de page de l'accueil. Politique d'usage CARTO : attribution obligatoire ; tuiles directes OK dans la limite du forfait gratuit (5 M / 1 M de requêtes/mois) ; au-delà du forfait, prévoir un fournisseur de tuiles ou l'auto-hébergement au lancement (même logique que le serveur OSRM démo de la v2.27, ADR 0002). Le correctif de l'accumulation de l'attribution après Plan → Satellite → Plan (signalé dans le rapport v2.44) est fait dans ce lot : l'ordre était `changer l'attribution → retirer → remettre` — or Leaflet retire au retrait l'attribution lue dans `getAttribution()`, donc la NOUVELLE (jamais affichée), et l'ANCIENNE restait, une ligne de plus à chaque bascule. L'ordre est désormais `retirer → changer l'attribution → remettre`.
7. **Inchangés :** Satellite Esri (plafond 18) ; palette UI « Nuit violette » ; ligne d'itinéraire rose, marqueurs, POI (sauf libellés ci-dessus) ; plafond Plan 19 (CARTO sert les zooms 0 à 20) ; `lib/commission.ts` non touchée ; les 2 règles intactes (barre de chargement partout ; switch passager → chauffeur impossible sans compte chauffeur).

## Preuves et limites de vérification

- **Ce qui a été lu (sources publiques, consultées le 15/11/2026) :** la définition du style CARTO dark matter — dépôt CartoDB/basemap-styles, `cartocss/web-styles/dark-matter.tm2/labels.mss` (via `shared/mss/labels.mss`), `style.mss` (variables : fond #090909, `@place_text` #444, `@road_text` #333), `project.yml` (source de tuiles vectorielles, couches `place` / `poi` / `transportation_name`) — et le style vectoriel actuel `https://basemaps.cartocdn.com/gl/dark-matter-gl-style/style.json` (couches `place_suburbs` z12–16, `place_hamlet` z12–16, `place_villages` z10–16, `place_town` z8–14, `place_city_*` z8–15 — aucune ne couvre `quarter`). La classification OSM des 57 quartiers vient de Photon (`photon.komoot.io`, recherche « <nom>, Libreville », objet `place` retourné) : 40 `suburb`, 1 `city` (Akanda), 1 `quarter` (PK5), 15 non retrouvés.
- **Ce qui n'a PAS pu être vérifié — limite de l'environnement, à lire avant de croire un résultat curl de cette VM :** le proxy de sortie de la VM intercepte les tuiles et renvoie un contenu FIXE par hôte (OSM = toujours les mêmes 6 725 octets / md5 8e8d1ff4, que ce soit Libreville ou Paris centre, tous sous-domaines confondus, même avec cache-buster ; CARTO `light_nolabels` / `light_all` = toujours 2 049 octets / md5 502fc5f6 ; CARTO `dark_all` ET `dark_nolabels` = toujours 2 513 octets / md5 df9307c7, identiques pour Paris et Libreville ; connexion directe sans proxy : échec, 0 octet). Un HTTP 200 ne prouve donc que l'hôte répond, JAMAIS le contenu d'une tuile. Aucune table de masquage n'a été construite en prétendant l'avoir vérifiée sur des tuiles réelles, et aucun rendu navigateur local ne montre les tuiles (elles ne chargent pas dans le navigateur de la VM : `ERR_TUNNEL_CONNECTION_FAILED`).
- **Réserve sur la vérification curl de la v2.41 :** les « 9 md5 distincts » (grille 3×3 au Centre-ville, tailles 4 157 à 10 812 o, 67 à 256 couleurs) ont été mesurés le 14/11, quand curl rapportait encore des contenus variés par tuile — un contenu fixe par hôte n'aurait pas pu produire ces variations, donc la vérification reste plausible. Mais elle ne peut plus être refaite ni confirmée depuis cette VM : c'est un fait de l'environnement, pas une faute de la v2.41. La preuve visuelle réelle du fond Plan actuel viendra de la vérification navigateur live après push et du téléphone du propriétaire.
- **Vérifications faites en local (honnêtes sur ce qu'elles prouvent) :** `npm run build` exit 0 ; `npm run docs:check` OK (35 blocs) ; rendus mobiles Playwright 390×844 (serveur dev port 3100) aux zooms 12/14/16/19 en Plan et en Satellite — vérifié DANS LE DOM : URL des tuiles Plan = `basemaps.cartocdn.com` avec la variante `dark_all`, attribution exacte présente, libellés Drive présents dans le DOM, aucun nom de quartier en double DANS LE DOM, 59 POI présents/cliquables, bascule Plan ↔ Satellite (plafonds 19/18 respectés) ; greps de propreté passés (aucun des marqueurs interdits par les règles du projet : nom personnel, mention d'origine artificielle du contenu, promesse différée, résidu du fond OSM dans le code Plan, `.map-tiles-dark` actif). **Non prouvé en local :** le chargement réel des tuiles, la lisibilité des rues sur fond sombre, l'absence de doubles sur les tuiles réelles — à confirmer en live après push.
- **Étape live restante (après push, avant de considérer le lot terminé) :** (1) créer la clé CARTO gratuite, la poser dans Vercel (`NEXT_PUBLIC_CARTO_API_KEY`), redéployer — sans elle, la carte affiche le filigrane ; (2) vérifier sur le téléphone du propriétaire, en plein jour : noms de rues lisibles sur fond sombre (z13–17), aucun quartier en double (z12–16 en Plan, PK5 visible seul, Akanda visible dès z15, Palais des Sports sans double dès z16), attribution « © OpenStreetMap contributors © CARTO » visible, bascule Plan → Satellite → Plan sans accumulation de l'attribution ; (3) selon le résultat : resserrer la table (doubles résiduels), retirer Akanda de la table (nom absent à z12–14), remettre PK5 (double « PK5 »), ou revenir au fond OSM clair (lisibilité insuffisante).

## Conséquences

- Le fond Plan dépend désormais d'une clé API gratuite CARTO : un compte CARTO à créer (par le propriétaire) et une variable Vercel à poser, sinon filigrane. C'est la première dépendance à clé du front (hors Supabase/Resend, côté serveur).
- La table anti-double change de sens : elle n'encode plus des observations de tuiles OSM, mais une lecture du style CARTO — son commentaire l'étiquette comme approximation, avec la procédure de correction live (point 3 de l'étape restante).
- Le fond du conteneur de carte passe en #191432 : la carte « respire » violet même avant le chargement des tuiles.
- Les entrées historiques du CHANGELOG et du README (v2.41, v2.42, v2.43) gardent leurs mentions OSM : elles décrivent des versions passées, on ne les réécrit pas.

## Alternatives écartées

- **`dark_nolabels`** : doubles réglés à la racine (aucun nom imprimé), mais rues sans noms à tous les zooms — inacceptable pour une appli de course, où l'on s'oriente aux noms de rues. Écarté sur le critère n° 2 (noms de rues visibles), après la lisibilité.
- **Garder le fond OSM clair (v2.41)** : lisible et sans clé, mais contraire à la demande explicite du propriétaire (15/11 ~07h44 : la carte aux couleurs de sa palette). Gardé comme plan de repli si la vérification live juge `dark_all` illisible.
- **Filtre CSS sombre sur les tuiles** (assombrir / teinter les tuiles vers #191432) : écarté — c'est exactement le procédé qui lavait les détails et que le propriétaire a fait retirer le 14/11 ; et rien ne permet de le prouver sans danger depuis cette VM (tuiles non visibles).
- **Style vectoriel personnalisé dès ce lot** (MapLibre + tuiles vectorielles CARTO, couleurs modifiables — vrai fond #191432, libellés clairs et lisibles) : c'est la solution qui donnerait un VRAI fond violet détaillé et lisible, mais elle change de bibliothèque de carte (Leaflet → MapLibre, ADR 0001) et de format de tuiles : hors périmètre de ce lot, à proposer comme lot ultérieur si la vérification live juge `dark_all` insuffisant.
- **Autres fonds sombres sans clé** : Esri World Dark Gray (quasi vide à Libreville, v2.7) ; Stadia (clé exigée, 401, v2.41). Aucun ne donne un fond sombre détaillé sans clé.
