# ADR 0022 — Point de départ et de destination précis : épingle déplaçable, adresse résolue, coordonnées exactes

- **Statut :** acceptée (15/11/2026, lot v2.47 — local, en attente de push). **Note v2.50 ([ADR 0025](0025-prix-distance-routiere-osrm.md)) : le point 3 de la décision (« Estimation sur les coordonnées exactes — par haversine, PAS par OSRM ») est REMPLACÉ — l'estimation est désormais calculée sur la distance routière OSRM entre les points exacts, avec repli vol d'oiseau marqué approximative. Le reste de cette ADR (épingle, géocodage inverse, validation serveur, GPS imprécis) est inchangé.**
- **Contexte :** le propriétaire envoie un enregistrement d'écran de 37 s d'une amie qui utilise Yango (15/11 ~09h04) : « Essaie de copier un peu leur interface et fonctionnalités ça c'est yango ». Sa priorité, dite ensuite (~09h06) : « La location est bien gérée et tout pour déplacement précis pick up adresse car la géolocalisation n'est pas souvent exacte et c'est chiant ». Chez Yango, le passager règle son point de départ exact en déplaçant la carte sous une épingle fixe (« Balayez pour déplacer la carte ») et l'adresse se résout à l'écran. Jusqu'ici, Drive ne connaissait que des quartiers : le départ et la destination étaient des noms de quartier, le prix était estimé depuis les centres de quartiers, et le chauffeur devait deviner où était le passager dans le quartier. Le lot copie le mécanisme, pas les textes ni la mise en page Yango (changement de cap du propriétaire, 15/11 ~09h20 : « Ne copie pas textuellement, innove, mets des effets, anticipe, prévois »).

## Décision

1. **Épingle centrale déplaçable, deux gestes.** Sur l'écran de commande, une épingle fixe au centre de la carte (sa pointe = le point exact) : le passager glisse la carte dessous (geste Yango) OU glisse l'épingle elle-même (geste ajouté — certains utilisateurs attrapent l'épingle, d'autres la carte). Les écouteurs sont natifs (`pointerdown` / `mousedown` / `touchstart` avec `stopPropagation` + `preventDefault`) : les événements React arrivent trop tard, Leaflet écoute plus bas. Pendant l'ajustement, le marqueur classique est masqué, le `fitBounds` est suspendu, et la rotation d'écran est gérée (`window resize` → `map.invalidateSize()` — manquait depuis toujours).
2. **Adresse résolue par le serveur, jamais inventée.** À chaque déplacement (debounce ~400 ms), le client appelle `GET /api/reverse-geocode?lat&lng` — jamais Nominatim directement depuis le navigateur (la politique d'usage exige un `User-Agent` propre et un espacement des requêtes, impossibles à garantir côté client). La route essaie Nominatim (`reverse?format=jsonv2`, zoom 18) puis Photon en repli, avec cache serveur 10 min (coordonnées arrondies à 4 décimales), espacement 1,1 s entre appels amont et timeout 5 s. Réponse `{ ok, address, area, source, cached }` ; `address: null` si les deux échouent — jamais d'erreur côté client. La feuille affiche « Point de départ : \<adresse\> — \<quartier\> » avec un squelette pendant la résolution (règle n° 1 : barre de chargement partout où il y a une attente) ; si la résolution échoue, elle affiche les coordonnées + le quartier le plus proche, avec un bouton « Réessayer ».
3. **Estimation sur les coordonnées exactes — par haversine, PAS par OSRM.** Le brief initial du lot disait « distance OSRM depuis le point précis » : il entre en conflit avec l'ADR 0010 et le commentaire verrouillé de `lib/geo.ts` (« Ne jamais remplacer cet appel par OSRM dans le calcul d'un prix »). Le prix reste calculé sur la distance haversine entre les deux points exacts (`estimateFareFromCoords` / `estimateTripFromCoords`, `lib/pricing.ts` — même modèle au km : Solo 500 + 210/km, Groupe 300 + 135/km, planchers 550/400, suppléments aéroport et piste ; le supplément aéroport reste déterminé par le quartier, pas par l'épingle). OSRM reste affichage et guidage uniquement (durée routière affichée dans la feuille récap, navigation chauffeur). L'écart est signalé au propriétaire : s'il veut le prix sur distance routière, c'est une décision à prendre avec lui, pas un détail d'implémentation.
4. **Confirmation et envoi des points exacts.** Bouton « Confirmer ce point » (départ et destination, chacun son panneau d'ajustement). La demande de course (`POST /api/rides`) envoie `pickupPoint` / `destinationPoint` (`{ lat, lng, address, neighborhood }`, null pour un centre de quartier) ; le serveur valide : coordonnées dans la zone de service (sinon 400 « Le point de départ/destination est hors zone — Stacks Drive est à Libreville pour l'instant » + retour au dernier point valide, sans bloquer), quartier du point = quartier du trajet, estimation recalculée côté serveur depuis les points exacts quand les deux sont là. **Migration `supabase/migration-v2.47-pickup-points.sql` écrite, NON exécutée** (6 colonnes sur `rides`, idempotentes) : sans elle, la validation serveur et l'estimation exacte fonctionnent, mais l'adresse précise n'est pas persistée — donc invisible côté chauffeur. Le code est résilient (patron 42703 : les 6 colonnes sont retirées de l'insert en cas de retry). La migration est indispensable pour que le chauffeur voie l'adresse : elle doit être exécutée avant le push, après approbation.
5. **GPS imprécis : on le dit, on ouvre sur l'épingle.** `getUserPosition` retourne désormais aussi `accuracyM`. Si la précision est > 50 m (ou si la géolocalisation échoue), la feuille affiche « Position approximative — déplacez l'épingle pour préciser » et l'épingle s'ouvre directement (au chargement et sur « Me localiser ») ; en cas d'échec GPS, le message dit quoi faire (« autorise la position dans ton navigateur, ou choisis ton quartier ») avec un bouton « Réessayer ».
6. **Côté chauffeur : l'adresse précise, pas le centre du quartier.** La page de course (`/courses/[id]`) affiche « Point de départ exact : {adresse} · {quartier} » et « Destination exacte : {adresse} · {quartier} » quand les adresses existent ; l'ETA et la navigation OSRM partent des coordonnées exactes (le `navTarget` est le point exact, pas le centre du quartier).
7. **L'existant est conservé.** Listes de quartiers triées + recherche (choix rapide : positionne l'épingle sur le quartier) ; « Me localiser » recentre l'épingle sur le GPS ; brouillon de trajet conservé (quartiers seulement — les points exacts ne sont pas persistés dans le brouillon local).

## Ce qui vient de Yango, ce qui est propre à Drive

| Écran / mécanisme | Inspiration Yango | Innovation Drive |
|---|---|---|
| Épingle déplaçable | Carte qui glisse sous une épingle fixe, adresse résolue | Deux gestes (carte OU épingle) ; épingle avec chute/rebond animée ; GPS imprécis détecté et annoncé ; hors zone géré sans bloquer |
| Adresse résolue | Adresse affichée à l'écran | Géocodage par proxy serveur (politique d'usage respectée, repli Photon, cache) ; échec = coordonnées + quartier + « Réessayer », jamais d'adresse inventée |
| Confirmation du point | Point confirmé avant commande | Le point confirmé est validé côté serveur (zone, quartier, estimation recalculée) ; retour au dernier point valide sans bloquer |
| Prix | Yango affiche un prix fixe | Drive affiche une ESTIMATION indicative recalculée sur le point exact — le prix final se négocie et se fige à l'acceptation (modèle Drive, jamais de prix fixe, jamais de surge) |

## Effets et anticipations

- **Effets :** épingle chute + rebond (`map-pin-drop`, rejoué via `centerPinKey` à chaque pose), tracé de l'itinéraire qui se dessine (`.route-draw`, suspendu pendant l'ajustement), transitions de phase de la feuille (`.sheet-phase-in`, 0,28 s), squelettes pendant la résolution d'adresse et le calcul du prix (pas de spinner brut), micro-interactions (`active:scale-95` sur les boutons).
- **Anticipations :** GPS coupé ou imprécis (avertissement + auto-ouverture de l'épingle + « Réessayer ») ; réseau lent (repli coordonnées + quartier, bouton « Réessayer » avec `geoRetryKey`) ; hors zone en direct pendant le glisser (avertissement + confirmation = retour au dernier point valide) ; adresse introuvable (repli + suggestion du quartier le plus proche) ; clavier qui masque la feuille (la feuille monte au cran 58 quand le champ de recherche prend le focus) ; rotation d'écran (`invalidateSize`).
- **Wording Drive (pas de copie littérale) :** barre flottante « Vers où ? » (pas « Où allons-nous ? »), consigne « Glisse la carte sous l'épingle, ou glisse l'épingle elle-même », « Confirmer ce point ».

## Preuves et limites de vérification

- `npm run build` exit 0 (43 pages, route `/api/reverse-geocode` présente) ; `npm run docs:check` OK (35 blocs) ; rendus mobiles Playwright 390×844 (serveur dev port 3100) : épingle centrale visible, feuille avec adresse résolue, état de chargement (squelette) ; greps de propreté passés (0 nom personnel, 0 mention d'origine artificielle du contenu, 0 clé secrète) ; les 2 règles vérifiées intactes ; estimation recalculée sur point précis testée (2 points du même quartier à distances différentes → 2 estimations différentes).
- **Non prouvé en local :** le géocodage réel (Nominatim / Photon) et la durée OSRM réelle — le réseau de la VM bloque les appels sortants directs (proxy) ; le code et le repli sont vérifiés, le flux réel doit être testé en live après push. La migration v2.47 n'est pas exécutée : tant qu'elle ne l'est pas, l'adresse précise n'apparaît pas côté chauffeur (le reste fonctionne).

## Conséquences

- Nouveau point d'entrée serveur `/api/reverse-geocode` (dépendance Nominatim/Photon, 1 req/s max, cache 10 min) : au lancement, le volume est faible et la limite suffit ; si le volume croît, prévoir Photon/Nominatim auto-hébergé ou un fournisseur payant (même logique que l'OSRM démo de la v2.27).
- La table `rides` gagne 6 colonnes (migration à exécuter une seule fois, après approbation) ; sans elle, le code dégrade proprement.
- `lib/commission.ts` intouchée ; les 2 règles intactes ; aucun nouveau cron.

## Alternatives écartées

- **Géocodage direct côté client (Nominatim depuis le navigateur)** : écarté — pas de `User-Agent` propre ni d'espacement garanti, et la clé de la politique d'usage serait exposée au volume de tous les clients. Le proxy serveur centralise la cadence et le cache.
- **Prix sur distance OSRM** : écarté — conflit avec l'ADR 0010 (prix sur haversine, jamais routière). La distance routière reste affichée (durée) mais ne fixe pas le prix.
- **Épingle déplaçable seule (sans glisser la carte)** : écarté — le geste Yango (carte sous l'épingle) est le plus naturel sur mobile ; les deux gestes coexistent.
